# Submission statements

Deliverables 2 and 3 from the contest rules: the written problem and solution
statements, and the written statement on how IBM Bob was used.

---

## Problem statement

AI coding agents can read a repository but hold no persistent memory of it.
Every session starts from nothing.

Three consequences, all of which land on a human reviewer:

1. **Duplicated capability.** The agent writes a function that already exists,
   because it never checked.
2. **Violated architecture.** It breaks a layering rule that no compiler
   enforces and no file states — the rule lives in the team's habits.
3. **Unsafe edits.** It modifies a component that is protected for a reason
   recorded nowhere in the source.

The third is the expensive one, and it gets worse with the age of the system.
On an IBM i or IBM Z codebase built over decades, the knowledge that governs
safe change is not in the code at all. It is in the architecture, the reuse
conventions, and the reasoning of engineers who have retired. An agent cannot
recover it by reading harder, and neither can a new hire.

This is a workflow problem, not a model problem. A better model still does not
know that `EMP_UPDATE` must be the only writer to the employee table, or that a
particular module is fragile for reasons that predate the current team.

## Solution statement

**ArchMemory** is an MCP server that gives an AI agent persistent, verified
memory of a codebase: an architecture graph, an index of existing capabilities,
the constraints that govern change, and the engineering decisions behind them.

The agent consults memory *before* writing and validates its own diff *before*
committing. The validation is deterministic — derived from the graph and the
constraint store, never from a model's judgement — so the same change always
produces the same verdict, and every verdict can be pointed at.

It runs from a single SQLite file with no external services, so it works
offline and adds no infrastructure to adopt.

**Measured on the real `psf/requests` library:**

- A diff reimplementing an existing capability is blocked, naming the function
  that already does it and the modules that depend on it.
- A diff importing `api` into `adapters` is blocked, citing the layering rule
  and its rationale — a rule that appears nowhere in the source.
- A diff editing the protected compatibility shim is blocked, citing the
  decision and the reason it was recorded.
- An unrelated new function passes. Calibrated over ten cases: 5/5 genuine
  duplicates caught, 0 false positives.

The workflow improved is **application maintenance and legacy modernization**:
the point at which a change is proposed and somebody has to decide whether it
is safe.

## How IBM Bob was used

Bob is on both sides of this system — it built ArchMemory, and it is a runtime
component of it.

### Bob built it

Every module was written by Bob in Agent mode across ten tasks, each recorded
as a session summary in `bob_sessions/` with its Bobcoin cost. Roughly **32
Bobcoins** produced 2,980 lines of Python and 679 lines of tests.

Bob features used, each because it fitted the work rather than to tick a box:

- **`/init` → `AGENTS.md`** — persistent project context carried across every
  later task, so each new task started informed without re-reading the repo.
- **Subagents and parallel tasks** — capability memory is generated by one
  subagent per module, each reading its module in an isolated context and
  returning structured descriptions the parent persists.
- **Document understanding** — the layering constraints are extracted from
  `docs/architecture.md`, written as ordinary engineering prose, not config.
- **MCP servers** — how Bob reaches memory at runtime.
- **Custom rules** — the mode-specific rule files generated at init.
- **Headless mode (`bob run`)** — the A/B experiment was run unattended, both
  arms driven by an identical command differing only by `--disable-mcp`.

### Bob is part of the running system

Asked whether `requests` already had a CIDR membership check, Bob called
`find_capability` over MCP and answered:

> *"`requests.utils.address_in_network` — checks whether an IPv4 address
> belongs to a CIDR subnet. If you're about to write something that checks
> IP-in-CIDR, reuse `address_in_network` directly rather than reimplementing
> it."*

That exchange cost 0.13 Bobcoins.

### What Bob contributed that we would have got wrong

- Bob's own test suite caught an off-by-one in relative-import resolution
  (`requests.adapters.utils` instead of `requests.utils`). Every architecture
  check depends on that resolution; the bug would have silently disabled the
  layering rules.
- Bob's `used_by` implementation is better than the reference: function-level
  and class-qualified, so `super_len` reports `PreparedRequest.prepare_body`
  rather than merely "the utils module".
- Bob's subagent-generated description of `super_len` — a function with **no
  docstring at all** — made it findable for the first time.

### A measured lesson about working with agents

Long-running tasks re-send their whole accumulated context on every message.
The same class of work cost **5.42 Bobcoins** inside a saturated 86.5k context
and **2.23** in a fresh task — 60% cheaper. Three later tasks together cost
3.35 against 12.78 for a single task run in a saturated context.

Starting a new task per unit of work was the single largest cost saving in the
project.
